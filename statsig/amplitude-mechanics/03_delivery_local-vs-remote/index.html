Both approaches deliver a variant. What differs is who computes the decision: Amplitude's servers, which can enrich the request with everything they know about the user, or your own SDK, which answers instantly but only knows what you hand it.

Pick a mode. Watch who answers and how long the round trip takes.
Remote is phoning HQ every time: "what should this shopper see?" HQ knows everything about them, their history, their cohorts, but the call takes time. Local is keeping a synced copy of the rulebook and answering instantly yourself, lightning fast, but you have to bring the shopper's details, because nobody at HQ is looking them up for you.

At AmpliStore the homepage hero test targets a "lapsed VIPs" cohort, so it uses remote evaluation, letting the servers enrich the request with cohort membership, geolocation, and history. The search-ranking experiment handles 30,000 requests a second, so it uses local evaluation with configs synced to the SDK, evaluated in-process in a fraction of a millisecond. The trade for local: no sticky bucketing, no enrichment, and cohorts match by User ID only. Server-side local also logs assignment events instead of exposures, so you use assignment as the exposure event in analysis.
